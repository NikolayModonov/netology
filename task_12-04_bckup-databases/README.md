## Задание 1. Резервное копирование (кейс финансовой компании)

### 1.1. Восстановление данных в полном объёме за предыдущий день

Можно использовать:
- Полное резервное копирование (full backup), выполняемое ежедневно (например, ночью).  
- Инкрементное или дифференциальное резервное копирование (чтобы сократить объём данных между полными бэкапами).  
- В случае сбоя восстанавливается последний полный бэкап, затем применяются инкрементные (или дифференциальные) за прошедшие сутки до момента сбоя.  
- Для PostgreSQL: `pg_basebackup` + WAL-файлы; для MySQL: `mysqldump` + binary logs.

### 1.2. Восстановление данных за час до предполагаемой поломки

Требуется восстановление на момент времени, Point-in-Time Recovery, PITR. Схема:
- Регулярные полные бэкапы (например, ежедневные).
- Постоянное архивирование журналов изменений (WAL в PostgreSQL, binary logs в MySQL).
- При восстановлении: разворачиваем последний полный бэкап, затем применяем все журналы изменений до нужного момента времени (например, за час до сбоя).
- В PostgreSQL это достигается настройкой `archive_mode` и `archive_command`, в MySQL – включением binary logging и использованием `mysqlbinlog`.

### 1.3. Моментальное переключение на работающую базу при поломке

Да, такой кейс возможен. Это реализуется с помощью:
- **Репликации** (master-slave или master-master) с автоматическим переключением (failover).  
- Использование инструментов кластеризации (например, Patroni, Repmgr, MHA, Orchestrator).  
- В случае падения мастера система автоматически переключает нагрузку на реплику, обеспечивая минимальное время простоя.  
- Дополнительно можно настроить синхронную репликацию, чтобы данные на реплике были актуальны на момент сбоя.

## Задание 2. PostgreSQL

### 2.1. Пример команды резервирования и восстановления

**Резервное копирование (pg_dump):**
+++bash
pg_dump -U postgres -Fc -b -v -f /backup/db_backup.dump mydb
+++
- `-Fc` – пользовательский формат (сжатый, можно параллельно восстанавливать).  
- `-b` – включать большие объекты.  
- `-v` – подробный вывод.  
- `-f` – файл назначения.

**Восстановление (pg_restore):**
+++bash
pg_restore -U postgres -d mydb -v /backup/db_backup.dump
+++
- `-d` – база данных, в которую восстанавливаем.  
- Можно также использовать `pg_restore` для создания скрипта SQL.

**Альтернативный способ (plain SQL):**
+++bash
pg_dump -U postgres mydb > /backup/db_backup.sql
psql -U postgres mydb < /backup/db_backup.sql
+++

### 2.1.* Автоматизация резервного копирования

Да, автоматизация возможна. Способы:
- Cron-задания – ежедневный запуск скрипта с pg_dump.
- Скрипты с ротацией – хранение бэкапов за последние N дней, удаление старых.
- Использование pg_basebackup + архивация WAL – для PITR.
- Инструменты – pgbackrest, barman – предоставляют готовые решения для автоматического резервирования и восстановления с retention-политиками.
- Мониторинг успешности бэкапов, уведомления при ошибках.

## Задание 3. MySQL

### 3.1. Инкрементное резервное копирование

В MySQL инкрементное копирование основано на "binary logs". Пример команды для создания инкрементного бэкапа (копирование логов за определённый период):

+++bash
mysqlbinlog --start-datetime="2026-09-01 00:00:00" --stop-datetime="2026-09-01 23:59:59" /var/log/mysql/mysql-bin.* > /backup/increment.sql
+++

Также можно использовать утилиту mysqlbackup (из MySQL Enterprise), но в открытых версиях инкрементальные бэкапы делаются через комбинацию полного бэкапа (например, mysqldump или xtrabackup) и последующего применения binary logs.

### 3.1.* Преимущества реплики перед обычным резервным копированием

- Нулевое влияние на мастер – бэкап можно снимать с реплики, не нагружая основной сервер
- Актуальность данных – реплика содержит состояние, близкое к реальному времени
- Быстрое переключение – при сбое мастера реплика может стать новым мастером с минимальным простоем
- Распределение нагрузки – реплика может обрабатывать запросы на чтение
- Отказоустойчивость – реплика является горячим резервом для высокой доступности
