# Домашнее задание к занятию «Компоненты Kubernetes»

Кластер Kubernetes состоит из двух основных частей: Control Plane (плоскость управления) и Worker Nodes (рабочие узлы).

## Компоненты Control Plane

- **kube-apiserver**: Центральный компонент, предоставляющий REST API. Через него проходят все запросы на управление кластером.
- **etcd**: Распределенная база данных типа ключ-значение. Хранит все конфигурации и состояние кластера.
- **kube-scheduler**: Планировщик. Отвечает за выбор подходящего узла для запуска новых подов.
- **kube-controller-manager**: Запускает фоновые процессы (контроллеры), которые следят за состоянием кластера и приводят его к желаемому виду (например, поддерживают нужное количество реплик).
- **cloud-controller-manager**: Взаимодействует с API облачного провайдера (управление балансировщиками нагрузки, дисками, узлами).

## Компоненты Worker Node

- **kubelet**: Основной агент на каждом узле. Следит за тем, чтобы контейнеры в подах были запущены и работали в соответствии с манифестами.
- **kube-proxy**: Сетевой прокси. Обеспечивает маршрутизацию трафика и балансировку нагрузки для сервисов.
- **Container Runtime**: Среда выполнения контейнеров (например, containerd или CRI-O). Отвечает за скачивание образов и непосредственный запуск контейнеров.

## Расчёт ресурсов приложения

Приложение (бекенд и фронтенд) вместе с базой данных и кешем упаковывается в Helm-чарт. Все параметры (количество реплик, запросы и лимиты ресурсов) выносятся в `values.yaml`, чтобы для каждого окружения можно было использовать свой файл конфигурации. Расчёт ниже выполнен для целевого окружения.

Так как в Kubernetes CPU - это условная единица, допустимо использовать доли ядра (millicores). Поэтому значение 0.2 ядра для фронтенда означает 200m CPU на один под.

| Компонент | Копий | CPU на копию | RAM на копию | CPU всего | RAM всего |
|---|---|---|---|---|---|
| БД | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| Кеш | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| Фронтенд | 5 | 0.2 | 50 МБ | 1 | 250 МБ |
| Бекенд | 10 | 1 | 600 МБ | 10 | 6 ГБ |
| Итого | 21 | | | 17 | ~30.25 ГБ |

Требований к диску в задании нет, поэтому закладываем примерные значения: для БД по 10 ГБ на копию (данные), для кеша по 10 ГБ на копию (персистентность RDB/AOF), для фронтенда по 1 ГБ (статика и образ), для бекенда по 1 ГБ (образ и логи).
Общий объём хранилища для volumes: 30 + 30 + 5 + 10 = 75 ГБ.

## Расчёт количества worker-нод

Выбираем сбалансированный тип worker-узла (8 vCPU и 16 ГБ ОЗУ), так как нагрузка смешанная: база данных и кеш требовательны к памяти (по 4 ГБ на копию), а бекенд - к процессору.

1. Для обеспечения отказоустойчивости БД и кеша их копии должны быть разнесены по разным нодам (с помощью pod anti-affinity). Поэтому архитектурный минимум - это 3 worker-ноды.
2. Общая нагрузка составляет 17 CPU и ~30.25 ГБ ОЗУ. На трёх нодах общая ёмкость будет 24 CPU и 48 ГБ. Утилизация составит около 70% по CPU и около 60% по памяти. Нагрузка помещается, но без должного запаса.
3. Закладываем резерв на отказ одной ноды (N+1). Если одна нода из трёх выйдет из строя, останется 16 CPU, а нам требуется 17 CPU. Поэтому добавляем четвёртую ноду.

Итого получаем 4 worker-ноды: общая ёмкость 32 CPU и 64 ГБ, утилизация около 55% по CPU и около 45% по памяти. При отказе любой одной ноды остаётся 24 CPU и 48 ГБ, и вся нагрузка комфортно помещается на оставшиеся три ноды.

## Служебные ресурсы нод

На worker-нодах часть ресурсов забирают ОС, kubelet, kube-proxy, container runtime, агенты логирования/мониторинга и eviction-порог. Для узла 8/16 закладываем резерв примерно в 0.5 CPU и 2 ГБ ОЗУ - то есть доступно для подов (allocatable) будет около 7.5 CPU и 14 ГБ.
Проверяем: 4 ноды дают 30 CPU и 56 ГБ доступной памяти против требуемых 17 CPU и 30.25 ГБ. При отказе одной ноды остаётся 22.5 CPU и 42 ГБ, что также проходит с запасом.

Диск worker-нод: ОС и системные компоненты занимают ~20 ГБ, образы и логи ~20 ГБ, а также доля на volumes (БД и кеш займут 60 ГБ из 75). Условно принимаем по 100 ГБ на ноду. Так как БД требует высокой скорости записи, используем SSD.

Для control plane служебная нагрузка другая: kube-apiserver, etcd, scheduler и controller-manager занимают ресурсы целиком, а приложения на них не размещаются (из-за taint). etcd чувствителен к скорости диска (WAL, fsync), поэтому здесь тоже нужен SSD.

## Ресурсы Control Plane

Кластер небольшой (21 под приложения и 4 worker-ноды), но для отказоустойчивости API и кворума etcd необходимо 3 CP-ноды. На каждую выделяем по 2 vCPU и 4 ГБ ОЗУ - это минимум для kubeadm с небольшим запасом. Диск - 50 ГБ SSD. Если используется managed control plane (например, Yandex Managed Service for Kubernetes), его ресурсы находятся на стороне провайдера и в этот расчёт не входят.
