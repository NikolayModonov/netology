# Домашнее задание к занятию «Компоненты Kubernetes»

Кластер Kubernetes состоит из двух основных частей: Control Plane (плоскость управления) и Worker Nodes (рабочие узлы).

## Компоненты Control Plane

- **kube-apiserver**: Центральный компонент, предоставляющий REST API. Через него проходят все запросы на управление кластером.
- **etcd**: Распределенная база данных типа ключ-значение. Хранит все конфигурации и состояние кластера.
- **kube-scheduler**: Планировщик. Отвечает за выбор подходящего узла для запуска новых подов.
- **kube-controller-manager**: Запускает фоновые процессы (контроллеры), которые следят за состоянием кластера и приводят его к желаемому виду (например, поддерживают нужное количество реплик).
- **cloud-controller-manager**: Взаимодействует с API облачного провайдера (управление балансировщиками нагрузки, дисками, узлами).

## Компоненты Worker Node

- **kubelet**: Основной агент на каждом узле. Следит за тем, чтобы контейнеры в подах были запущены и работали в соответствии с манифестами.
- **kube-proxy**: Сетевой прокси. Обеспечивает маршрутизацию трафика и балансировку нагрузки для сервисов.
- **Container Runtime**: Среда выполнения контейнеров (например, containerd или CRI-O). Отвечает за скачивание образов и непосредственный запуск контейнеров.


## Расчёт ресурсов приложения

Приложение (бекенд + фронтенд) с БД и кешем упаковывается в Helm-чарт: количество реплик, requests и limits каждого компонента выносятся в values.yaml, для каждого окружения — свой values-файл. Расчёт ниже выполнен для целевого окружения.

Примечание по CPU: в Kubernetes это условная единица, допустимы доли ядра (millicores), поэтому 0.2 ядра для фронтенда — это 200m CPU на под.

| Компонент | Копий | CPU на копию | RAM на копию | CPU всего | RAM всего |
|---|---|---|---|---|---|
| БД | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| Кеш | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| Фронтенд | 5 | 0.2 | 50 МБ | 1 | 250 МБ |
| Бекенд | 10 | 1 | 600 МБ | 10 | 6 ГБ |
| **Итого** | **21** | | | **17** | **~30.25 ГБ** |

Требования к диску в задании нет, поэтому принимаем допущения: БД — 10 ГБ на копию (данные), кеш — 10 ГБ на копию (персистентность RDB/AOF), фронтенд — 1 ГБ на копию (статика и образ), бекенд — 1 ГБ на копию (образ и логи).

Объём на volumes: 30 + 30 + 5 + 10 = **75 ГБ**.

## Расчёт количества worker-нод

Берём worker-узел 8 vCPU / 16 ГБ — сбалансированный тип под смешанную нагрузку (часть подов тяжёлых по памяти — БД и кеш по 4 ГБ, часть по CPU — бекенд).

1. БД и кеш отказоустойчивы, их копии разнесены по разным нодам (pod anti-affinity) — минимум 3 worker-нод уже необходимо по архитектуре.
2. Нагрузка: 17 CPU и ~30.25 ГБ. На 3 нодах capacity 24 CPU / 48 ГБ — утилизация 71% по CPU и 63% по памяти. Нагрузка помещается, но без запаса.
3. Запас на отказ одной ноды (N+1): если одна нода из трёх выйдет из строя, останется 16 CPU — меньше требуемых 17 CPU. Добавляем четвёртую ноду.

Итого 4 worker-нод: capacity 32 CPU / 64 ГБ (утилизация 53% / 47%). При отказе любой одной ноды остаётся 24 CPU / 48 ГБ — вся нагрузка помещается на оставшиеся три ноды.

## Служебные ресурсы нод

Для worker-нод: часть ресурсов каждой ноды занимают ОС, kubelet, kube-proxy, container runtime, агенты логирования/мониторинга и eviction-порог. Для узла 8/16 закладываем резерв ~0.5 CPU и ~2 ГБ ОЗУ → allocatable ≈ 7.5 CPU / 14 ГБ.

Проверка: 4 ноды дают 30 CPU / 56 ГБ allocatable против требуемых 17 CPU / 30.25 ГБ — помещается. При отказе одной ноды: 22.5 CPU / 42 ГБ — также помещается.

Диск worker-нод: ОС и системные компоненты ~20 ГБ, образы и логи ~20 ГБ, доля на volumes (БД и кеш — 60 ГБ из 75) → принимаем **100 ГБ SSD** на ноду (БД требует быстрый диск).

Для control plane служебная нагрузка другая: kube-apiserver, etcd, scheduler, controller-manager занимают ресурсы целиком, приложения на CP не размещаются (taint). etcd чувствителен к скорости диска (WAL, fsync), поэтому SSD.

## Ресурсы Control Plane

Кластер небольшой (21 под приложения, 4 worker-нод), но для отказоустойчивости API и кворума etcd нужно 3 CP-нод. На каждую: 2 vCPU / 4 ГБ — минимум kubeadm для control plane с запасом, диск 50 ГБ SSD. Если используется managed control plane (например, Yandex Managed Service for Kubernetes), его ресурсы на стороне провайдера и в расчёт не входят.
